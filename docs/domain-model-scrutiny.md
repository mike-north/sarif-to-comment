# Domain model scrutiny

Candidate reasoning record · September 27, 2026 · Before milestone or implementation design

## Consumer statement and status

> Give the tool the feedback you want to contribute to a particular revision of a PR. Optionally supply proposed changes, either already in SARIF or through staged edits. It preserves what you mean, checks whether the complete contribution can be published, and presents it through the host's ordinary review mechanisms. If publication becomes uncertain, continue the same publication without blindly creating duplicates.

**Recommendation, moderate confidence:** The product can have a small conceptual surface without reducing its agreed capabilities. Keep feedback, proposed change, source association, and destination explicit. Combining, enriching, assessing, rendering, publishing, recovering, and cleaning up are behaviors over those meanings; they do not each require another user-managed entity or intermediate format.

The [decision log](design-decisions.md) remains authoritative. This document challenges the model that could implement those decisions; it does not adopt public field names, packages, commands, storage, or a milestone. The [specification](specification.md) supplies requirement and acceptance IDs. The user's current [attached domain-modeling guide](</Users/mnorth/.codex/attachments/7500b802-f6bd-4fac-8250-94e5eff7332f/Pasted text.txt>) supplies the approach: ordinary-language meaning, independent variation, query catalog, and making additional representations earn their place. It matches the local guide inspected during this work. Its example domains are not imported here.

The agreed default for valid feedback that cannot be placed inline is a general review comment with its exact-revision source permalink. Earlier documents may still call that default open; that wording must not reopen the accepted choice. Draft reviews are the default. Suggestion PRs are provisionally enabled by default, with explicitly low confidence pending real user experience.

## 2. Observations before implications

**Reality and observed evidence:**

- SARIF already represents feedback, producer attribution, file references, and standard region-edit fixes. The [new-file research](new-file-representation-research.md) found an extension path for explicit whole-file operations; it did not establish a final convention.
- A staged index contains a concrete intended repository state. It does not, by itself, explain a change or say which distinct edits must be accepted together.
- GitHub comments, native suggestions, reviews, and PRs have different host behavior. The [grouped-suggestion experiment](grouped-suggestion-experiment.md) established one same-repository, two-file proposal accepted through one PR. It did not implement this converter.
- The [lifecycle experiment](companion-pr-lifecycle-experiment.md) established that abandonment can leave a suggestion open. PR closure and branch deletion were separate observations; automatic branch deletion was disabled.
- The [publication-recovery experiment](publication-recovery-experiment.md) discarded successful creation responses, recovered the same unlabelled suggestion and pending review through their distinct markers, and resumed the missing label/link without issuing another creation. It did not inject a transport failure or prove concurrency, delayed visibility, or crash/restart behavior.
- Remote creation can have an uncertain outcome from the caller's perspective. A reference identifies the original PR; it does not distinguish several suggestions for that original.

**Architectural implications proposed here:**

- Reuse SARIF as the interchange representation instead of introducing a second public review-document format.
- Represent one proposed change independently of its eventual native suggestion, text presentation, or suggestion PR.
- Preserve explicit acceptance boundaries in the change itself. A separate group registry does not yet earn its cost.
- Give a publication enough durable identity and intended-effect information to resume. Do not promote every recovery identifier to a public domain resource.

These implications need the stress checks below; the observations alone do not prove them.

## 4. Candidate concepts, ownership, and identity

This is a conceptual inventory, not a list of classes or tables. “Owns” means responsibility for meaning and truth, not mandatory nesting in JSON. Feedback/change cardinalities below describe cases the product must preserve; they do not mandate a generic many-to-many graph or a relationship management API. Start with supplied SARIF relationships and the associations derived from the shared staged snapshot. Add internal indirection only when a concrete case needs it.

| Concept                    | Meaning and owner                                                                                                                                                                           | Identity and relationships                                                                                                                                                                                 | Why it survives removal                                                                                                |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| **Feedback**               | Supplied explanation, origin, relevant source associations, and any declared approval hold. The producer owns the judgment; this tool preserves it.                                         | Input-local identity/provenance is sufficient unless an upstream identifier exists. It can support no proposed change, one change, or alternative changes. Several feedback items can support one change.  | A patch alone cannot express feedback-only input, attribution, or several reasons for one edit.                        |
| **Proposed change**        | The repository change offered for acceptance, preserving any explicitly supplied requirement to accept its constituent operations together. The upstream producer owns intent and grouping. | Operations refer to files/content. Feedback relates to the change; no mandatory one-to-one ownership. Identity within an input or frozen publication is sufficient; no global proposal service is implied. | Removing it leaves only text or host actions and loses the same proposal across presentation forms.                    |
| **Source association**     | The file/content and optional region that feedback concerns, with enough provenance to interpret it.                                                                                        | A reference to a particular reviewed revision, or to explicit proposed content; includes path and optional region. It is a value/relationship, not necessarily an entity.                                  | Without it, the same line number can silently name different content or a nonexistent file.                            |
| **Review context**         | The destination original PR, reviewed revision, and caller policy needed to interpret and publish the contribution. The caller supplies intent; host inspection supplies current facts.     | The original PR has a host identity. The reviewed revision is a source identity. Neither is replaced by the current head or by a suggestion PR ID.                                                         | Identical feedback can be valid in one source/destination context and invalid in another.                              |
| **Publication occurrence** | One intention to publish a fixed complete contribution under a particular context and policy, including its recovery. This tool owns progress knowledge.                                    | Stable occurrence identity; each intended remote object also has its own stable identity. Network retries reuse these identities. A changed input is not silently the same occurrence.                     | Without this distinction, retrying after uncertainty cannot be separated from intentionally publishing another review. |

### What does not need to become another domain entity

- **Review contribution** names the complete supplied feedback and proposals being assessed together. It need not have a second public schema or a persistent identity before publication. This term avoids confusing the whole contribution with GitHub's review object, which may carry only part of its presentation.
- **Fix, remedy, and proposed change** should not become three competing domain layers. Use **proposed change** for the meaning and SARIF **fix** for its standard representation. “Remedy” may remain explanatory prose. A fix's operations and any alternative relationship still matter.
- **Group** is presently an acceptance relationship among operations, carried by the proposed change. It is not a workflow, an inferred dependency graph, or a certification of correctness.
- **Operation** is necessary semantics within a proposed change: replace content, introduce a file, remove a file. This does not justify independently managed operation resources. Deletion must remain distinguishable from replacing all content with an empty string.
- **Artifact** is SARIF's representation of a file description/content. Do not copy this into a parallel public `FileProposal` model merely because a change references it. An artifact can also be legitimate analysis context without participating in a fix.
- **Reviewed snapshot and staged snapshot** identify different sources of truth. They can use shared mechanisms for reading versioned file content; they are not interchangeable. The staged index is an enrichment input, not a second PR or a new author-visible revision lifecycle. Proposed content may be supplied in SARIF with no index at publication time.
- **Prepared artifact, rendered comment, exception report, and publication assessment** are representations or operation results. An assessment's blockers are meaningful, but do not imply a stored `ReadyReview` entity or a readiness state that remains true forever.
- **Remote review, comment, branch, commit, and suggestion PR** are real host objects. Keep their different lifecycles in the host integration. Do not force users to construct a generic remote-object graph to publish feedback.

### Three roles that can share reference mechanics

| Role                        | Question answered                          | Example                                                                                                                   |
| --------------------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| Feedback source association | What is the explanation about?             | The implementation that lacks documentation, or line 1 of the supplied proposed page. Feedback may also have no location. |
| Proposed operation target   | What repository content would change?      | Create `docs/feature.md`, regardless of where the explanation is associated.                                              |
| Host display anchor         | Where can the host show this contribution? | A changed implementation line, a general review body, or the suggestion PR's discussion.                                  |

These are roles, not three new entity types. They may coincide but cannot be derived from one another unconditionally. A general comment's exact-source permalink uses the feedback's verified reviewed-source association; a file that exists only in the proposal cannot receive a fabricated permalink into the reviewed tree. Its path and proposed-content reference remain explicit instead. Moving presentation does not change the edit target.

### Acceptance identity is not edit equality

Three fixtures distinguish the minimum required relationships:

1. **Several explanations, one actual staged replacement.** Two results discuss the same extracted replacement. Preserve both results' origins and render one replacement. This can be a composition of supplied feedback plus one derived change; no globally deduplicated proposal resource is required. **[D4; A2]**
2. **One explanation, alternative fixes.** One result offers “use parser A” or “use parser B.” The alternatives remain separate offers. Never union their edits or infer joint acceptance from containment in the same result. **[D7, D23]**
3. **Several explanations, one supplied multi-file acceptance unit.** One explanation motivates a code fix, another its regression test, and supplied grouping says to accept both together. Render one suggestion PR carrying that unit, retaining both explanations. Separate source associations do not split it. **[D4, D22; A29]**

If the same physical edit appears in two different alternatives or acceptance units, byte equality does not prove those proposals are the same. Sharing an internal edit value is possible; merging their acceptance identities is not justified. Conversely, copying the same staged replacement once per explanation would manufacture duplicate proposed work. This distinction is more precise than the initial shorthand “many-to-many feedback and changes”: the requirement is to preserve supplied alternative/joint relationships and known shared operations, not to build a general graph.

**Clarification candidate for R4:** Its “irreconcilable mechanical conflicts” wording should distinguish jointly intended edits from intentionally alternative remedies. In the parser example, inability to apply A and B simultaneously does not invalidate the offered choice. A complete publication preserves all supplied alternatives; completeness does not mean that every offered remedy must be applied together. D7/D23 support preserving alternatives without unioning them. The exact supported SARIF cases and faithful host presentation have not been established by the live experiments, so this reasoning is not a claim that alternative-fix publication is implemented or verified. A representation that cannot retain the choice must diagnose that limitation, not choose a winner.

### Independent variation checks

1. Change GitHub display from inline to general: feedback, origin, proposal, and source association stay the same; presentation changes.
2. Add a second reviewer explanation for the same staged replacement: feedback cardinality changes; the replacement does not multiply.
3. Switch a proposal from native suggestion to suggestion PR: proposed meaning stays the same; remote objects and acceptance mechanics change.
4. Advance the author's branch: reviewed source identity stays the same; current host eligibility may change. This is not automatic invalidation or reapproval.
5. Retry after a lost response: publication and object identities stay the same; observation and progress knowledge change.
6. Intentionally publish the same SARIF again: a new publication can exist without inventing new identities for every feedback item. Cross-invocation deduplication is not implied.

### An unresolved association is not evidence of another entity

Suppose one staged replacement overlaps several findings, while another staged file has no supplied explanation. The index tells us the changes, and source association can connect the overlapping findings. It does not invent the missing rationale or a joint acceptance requirement. Exact extraction/association rules still need fixtures under O3. Introducing an `AssociationWorkflow` or `ProposalGroup` entity would rename the uncertainty without answering it.

## 7. Questions the model should answer directly

| Consumer question                                          | Known information and answer path                                                               | What the caller should not reconstruct                                                     |
| ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| What feedback am I publishing, from whom, about what?      | Input contribution → feedback → origin and source associations.                                 | Host-comment cardinality or branch names as a substitute for source provenance.            |
| What exactly is the author being asked to accept together? | Proposed change → explicitly supplied member operations.                                        | Semantic grouping from a shared file, index, or PR title.                                  |
| Why did this become general feedback or a suggestion PR?   | Source/operation eligibility + caller policy → selected presentation.                           | Policy inferred from whichever API request happened to succeed.                            |

| Did this publication finish?                               | Publication's intended effects → verified remote observations and unresolved effects.           | A marker match interpreted as proof of complete success.                                   |
| Will resuming create a second suggestion?                  | Same occurrence and exact object identity → recovery before another create.                     | A recent-list miss interpreted as proven absence.                                          |

## 8. Smallest plausible interaction surface

Only now is an interface sketch useful. These are **actions and information**, not proposed command names, signatures, or a public object model:

1. **Combine/enrich:** supplied SARIF and, optionally, reviewed source plus staged changes → SARIF and any repair diagnostics. Preserve all producer meanings; strict/best-effort controls output on failure.
2. **Publish or resume:** SARIF plus original PR, reviewed revision, and policy → a draft or explicitly submitted review contribution, with a resumable record and an accurate outcome. The same publication entry point can continue an existing publication from that record. Normal publication performs its own complete assessment; a separate approval ceremony or mandatory prepare call is unnecessary. Input changes must not be silently folded into an uncertain earlier publication.
3. **Clean up suggestions:** a repository or known original PR plus caller authority → verified closures and clearly reported leftovers. No background service is implied.

Defaults carry much of the ordinary experience: draft code review; valid non-inline feedback as a general comment with exact-source link; native suggestions for eligible small changes; suggestion PRs allowed provisionally. Strict/best-effort belongs to combination/enrichment, not publication. Approval override, submission, and disabling suggestion PRs remain explicit choices with their existing meanings.

The surface need not expose render plans, operation IDs, proposal-branch construction, lock objects, snapshot registries, or per-object markers. Internal representations are justified only where they simplify validation or recovery without requiring users to manage them. A single opaque local recovery record can hide several stable remote-object identities while retaining them correctly.

## 9. Remaining decisions and the handoff boundary

### Product questions genuinely still open

- **Initial host/support envelope:** GitHub is the worked destination; GitLab remains relevant. The model does not require deciding every host before implementation, but any milestone must name its actual support rather than pretend a narrow slice implements the full product.
- **Immediate-submission action:** Submitted mode is agreed; whether callers choose comment/approve/request-changes events remains unspecified. Severity must not implicitly choose that action. This is product policy when that mode is scoped.
- **Suggestion PR default validation:** Enabled by default is already the provisional decision. Test its impact on real PR clutter and organization automation before treating it as permanent. No new decision is needed to preserve the current default.

### Engineering contracts still needed, without expanding the domain

Approval metadata syntax; exact SARIF extensions for whole-file operations and supplied groups/alternatives; index-to-feedback association; supported path/content/region cases; resource and comment limits; historical-source host eligibility; durable recovery, concurrency and observation rules; archival failure handling; and exact discovery pagination all remain concrete design work. They need explicit examples and tests before implementation, but do not each require new product concepts or user policy questions. Where a proposed rule would discard meaning or narrow a promised capability, it must be surfaced as a scope/product choice instead.

**Current judgment:** The core concepts have stopped shrinking under useful collapse. The model is simple enough to discuss a milestone after review of these boundaries, but this document does not prove a minimum architecture or authorize implementation. The strongest remaining challenge is whether the feedback-to-proposed-change relationships and explicit acceptance boundaries can be represented faithfully in ordinary SARIF plus a small extension, without importing a second review-document model. The next design artifact should test a handful of concrete SARIF examples against this model before choosing public field names.

**Handoff summary:** Preserve feedback, proposed change, source association, review context, and a recoverable publication occurrence. Remove assumptions that every review needs staged extraction, every finding owns a separate patch/comment, every preparation phase needs a new entity, or cleanup needs a local relationship database. Retain real distinctions between feedback and changes, reviewed and proposed content, atomic acceptance and publication completeness, remote effects and request attempts. The stress cases above explain why those distinctions remain.

### Implication for a first milestone

**Recommendation, not a selected implementation scope:** Start with complete supported SARIF producing one GitHub draft review: feedback-only input, a declared subset of existing-file replacements, exact-source general fallback, whole-contribution validation, and resumable publication of that one host review. This exercises the central feedback/proposed-change/source/presentation boundaries without requiring a new public format. Staged enrichment, whole-file/group publication through suggestion PRs, and cleanup remain explicit subsequent increments of the same model. A milestone must report unsupported input rather than silently omit it, and must not advertise the full suggestion-PR capability before implementing it.

Before turning that recommendation into implementation tasks, use concrete examples to settle the alternative-fix distinction and the supported SARIF profile. Do not add new domain entities merely to name those outstanding contracts. No implementation starts as a consequence of this document alone.
