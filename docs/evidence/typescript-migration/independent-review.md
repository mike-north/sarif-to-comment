Method: read `git diff -M -w` of every converted runtime module against 2829530 (publication, github, prepare-review, staged-changes, cli, sarif-common, staged-git, artifact-files, publish-sarif-review vs index.cjs), compared error-literal sets for the rewritten modules (sarif-authoring, sarif-inspection, placement, replacements), read release-guard/api-docs/build/build-manifest/check-types, workflows, tsconfigs, eslint config, the rollup and API report diff, the test narrowing helpers and the seam/consumer type tests, and cross-checked against evidence/final/VALIDATION.txt and p3/p4.

### CONFIRMED

**1. [risk — release safeguard weakened] API-report / reference-docs freshness gate is vacuous in CI and the publish workflow.**
- `.github/workflows/ci.yml:49-53` and `.github/workflows/publish.yml:78-84` now run `pnpm run build` *before* `pnpm run check`. `scripts/build.mts` calls `scripts/api-docs.mts build`, whose `build` branch is `generate(process.cwd())` (`scripts/api-docs.mts:102-104`), i.e. it overwrites the checked-in `api-report/sarif-to-comment.api.md` and `docs/api/` in the working tree. `check:api` then compares those (already regenerated) files with a sandbox regeneration → always "up to date".
- Old (2829530) CI ran only `pnpm run check` on the committed tree, so a stale committed report failed CI. New test `test/release.test.mts:988-990` pins the new order (`install`, `build`, `check`), so the weakening is entrenched by a test; no workflow step runs `git diff --exit-code` (grep of `.github`, `scripts`, tests: no hits).
- Failure scenario: a PR edits a `@public` TSDoc/type in `src/*.cts` without rebuilding and committing `api-report/` + `docs/api/`. CI is green; the API change never appears in the reviewable api-report diff; main carries stale docs until someone rebuilds. (The tarball itself ships fresh docs, so consumers are not harmed — this is a review/audit gate loss, which is why I rate it risk rather than defect.)
- Minimal fix: add a step after `pnpm run build` in both workflows: `git diff --exit-code -- api-report docs/api` (and pin it in `release.test.mts` next to the step-order regex). Alternative: let `build` write only `dist/` + the rollup, and have `check:api` generate the report/docs into its sandbox only.

**2. [nit] `prepare-review.cts:990` condition rewritten from `invocation.executionSuccessful === false` to `!invocation.executionSuccessful`.**
Equivalent only because the vendored schema lists `executionSuccessful` in `invocation.required` (checked: `definitions.invocation.required = ["executionSuccessful"]`) and the document is schema-validated before `analyzeRun`. Not a behavior change; worth a comment so a later relaxation of validation does not turn a missing field into `invocation-failed`.
