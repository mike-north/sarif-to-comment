# Independent modeling brief

This records the problem and behavioral requirements supplied to the fresh agent. It received no conversation history, existing domain model, decision log, or specification file. It was instructed not to inspect workspace files, memories, other agents or prior reports, and to return its answer without writing files.

## Problem

A developer wants to turn code-review feedback from humans, AI assistants, and analysis tools into an ordinary review on a hosting service, initially GitHub, without hand-constructing comments, source coordinates, or application controls. SARIF is the input/output interchange format. The tool is deterministic and does not decide whether feedback is correct, useful, or worth sending. Seek the simplest conceptual model and interaction surface that satisfy the behavior, rather than a general platform.

## Behavioral requirements supplied

1. Inputs may come from several producers. Preserve supplied explanations, attribution, relevant source references and suggested changes. Valid feedback may have no suggested change and may have no file/line association. Already complete SARIF must be usable directly.
2. Optionally, a developer edits and stages changes in a shared Git checkout. The tool derives the exact suggested edits from the intended staged content relative to the revision being reviewed and combines them with supplied SARIF feedback. It must not use unstaged working-tree content, invent explanatory reasoning, or infer semantic dependencies merely from proximity or a shared checkout.
3. Several explanations may refer to the same actual replacement range; presenting that replacement once must retain those explanations and their origins. Nearby feedback outside that range must not enlarge it. Do not assume every explanation corresponds to exactly one edit or one displayed comment.
4. Users may suggest modifying existing text, adding a whole file, or deleting a whole file. Deleting and emptying are different. A recommendation to add missing documentation may refer to line one of the proposed new page, although that page does not exist in the reviewed revision. Preserve full contents and intended path without inventing an existing line or a second critique of the proposed page.
5. Some supplied edits must be accepted together, such as a code change and its regression test, including multiple new files. Preserve that explicitly supplied requirement. Other supplied fixes can be alternatives; never silently combine mutually exclusive choices or infer their selection. Choosing semantic winners is upstream work.
6. Keep feedback bound to the explicitly reviewed revision even if the author's branch advances. Verify references against the content they actually name. A nonexistent line is an error. Valid feedback that GitHub cannot place inline should default to general review feedback with an exact source link where that content exists. Do not pretend general text retains unavailable click-to-apply behavior.
7. Prefer GitHub native suggestions for small eligible edits. A caller can allow or disallow creating additional PRs targeting the author's PR branch. When allowed, prefer these PRs for file additions/deletions and use one for explicitly supplied edits requiring joint acceptance. When disallowed, individual file additions/deletions may still be faithfully shown as ordinary feedback with supported convenience links, but a requirement for joint application cannot be silently split or omitted; report that it needs the setting enabled. Allow these PRs by default provisionally, recognizing PR clutter and organization automation costs may change that default after user feedback. Creation proposes changes; accepting them into the author's branch remains the author's action.
8. Any created additional PR includes a configured label and an ordinary reference to the original PR in its body. Do not require permission to edit the original's description. GitHub exposes references between PRs. An authorized caller can later find open labeled PRs, check whether the originals have ended, and close eligible leftovers. Lack of access or a failed lookup is not evidence that an original ended. PR closure and deleting a source branch require separate authority and are separate outcomes. A continuously running service is not required.
9. Validate the complete supplied material before any publication writes. Do not publish a supposedly safe subset when some required content cannot be faithfully represented or some item explicitly awaits approval. Ordinary SARIF without approval metadata needs no approval stamp. A deliberate override may ignore an explicit approval hold, but cannot bypass other failures. This tool does not manage proofreading, feedback-edit history or inferred approval staleness.
10. Leave a GitHub code review as a draft by default; immediate submission is an explicit choice. Associated additional PRs may be drafts with normal repository visibility. No extra privacy or holding service is required. Do not infer an approve/request-changes review action from finding severity.
11. GitHub can persist a requested creation while its response is lost; the caller might not receive the new object's ID. A retry of the same intended publication must investigate existing remote state before creating duplicates, distinguish several created PRs and the code review, and finish missing work accurately. A successful create or discovery of one remote item does not establish that all requested work finished. An immediate empty lookup does not prove no creation occurred. Treat an intentional new publication separately from resuming uncertain earlier work. Do not expand this into reconciliation of all historical reviews.
12. In the optional local combining/derivation step, strict failure produces diagnostics without a purported successful output; best effort preserves representable flawed material in a clearly distinguished error artifact and gives actionable diagnostics. Preserve earlier successful output under a historical name based on original creation time, and do not leave it at the normal success path after a failing rerun. Diagnostics identify what actual input to repair and what a rerun must establish. They are for people/agents, not a new mandatory machine protocol. A hold on sending must survive this step but does not itself make derivation fail.
13. Literal input content must remain literal, not executed or fetched merely because a source reference names it. Do not silently truncate or omit material, fabricate evidence, or send content to another service as a size-limit workaround. Detailed support bounds require explicit verification.
14. Preserve scope honesty: GitHub is the initial worked host; other review hosts may follow. Same-repository workflows come first. Fork permissions are a future case to accommodate conceptually without turning them into an initial implementation gate. No package publication is needed now.

## Requested reasoning

Independently derive a domain model. Start with the consumer-understandable meaning, then identify the smallest necessary distinctions, responsibilities, relationships, cardinalities, identity and lifecycles. Explain why each retained distinction is necessary with concrete examples. Try merging concepts and show where those attempts succeed or fail. Distinguish domain meanings from serialization, presentation and implementation machinery; do not assume they must all be entities or classes. Include questions the model lets callers answer, a minimal interaction surface (not fixed command/API syntax), and at least three new realistic stress scenarios not simply restating the numbered examples. Highlight ambiguity or inconsistency in the requirements rather than choosing unstated product policy. Do not design a large schema or implement code. There is no preferred answer and no reward for minimizing a concept count at the expense of meaning.
