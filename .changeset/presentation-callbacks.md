Customize how a review reads from library code. `publishSarifReview` and `validateSarifReview` accept `options.presentation`, a set of functions that return the Markdown of named review elements: `finding`, `attribution`, `alternatives`, `fileAddition`, `fileDeletion` and a suggestion pull request's `lifecycleNote`. Each receives the element's data, its built-in Markdown (`markdown`) and the fragments the result must keep (`required`); elements left out keep the built-in presentation, which is unchanged byte for byte. A callback changes how an element reads, never what is published or how it is identified: the tool still places every finding, appends native suggestion blocks exactly as validated, adds the review's publication marker and each suggestion pull request's structured marker last, and counts the customized text toward the size limits. A result that is not a non-blank string, omits a required fragment (exact proposed content and file details, a deletion's permalink, a finding's attribution and alternatives, the producers' names), could open a suggestion block, leaves a code fence or raw HTML open, contains marker text, adds raw HTML or a link reference definition of its own (one whose exact text the built-in Markdown contains may pass through), hides a required fragment (inside raw HTML, code it does not open, an image, a definition or an undisplayed element, or a permalink used as an image source or as the text of a link elsewhere), or (for `attribution`) spans several lines is refused with a `TypeError` before anything is written. Callbacks are not part of the publication identity, have no command-line equivalent, and are typed by the new public `IReviewPresentation` and its context interfaces. Links in review Markdown now all come from one builder, with unchanged output.
